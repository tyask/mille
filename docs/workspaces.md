# ワークスペース

Milleのワークスペースは利用者の作業場所です。今回追加するのは所属と招待の基盤で、献立・健康・栄養データの保存や共有はまだ行いません。

## 作成と選択

個人用は作成者本人だけが利用し、共有用は招待された利用者が参加します。共有用に参加人数の固定上限はありません。
種類は作成後に変更できません。名前は前後空白を除いて1〜80文字です。
所属がない利用者が初めてワークスペースを開くと「個人のワークスペース」を作成します。
同時に開いても初期作成を重複させません。

選択中のIDは利用者ごとにブラウザへ保存します。URLの `workspace` 指定も所属一覧と照合し、
削除済み・未所属など無効な指定は本人の一覧の先頭へ戻します。ブラウザ保存が無効でも操作できます。

## 所属と権限

OWNERとMEMBERは、所属するワークスペースの名称変更・招待・削除を行えます。
個人用への追加参加、退出、所有者移管は提供しません。
削除には現在のワークスペース名の完全一致が必要です。関連する所属・招待も削除します。
最後の所属を削除した後は、次回の一覧取得で個人用を作成します。

画面・APIは既存のAuth.jsセッションから内部利用者IDを確定し、登録・有効状態・メールを毎回DBで再確認します。
DB処理でも同じID・メール・現在の有効状態・所属を確認します。利用停止後は既発行セッションでも操作できません。
利用者別の応答は `private, no-store` とし、更新APIは同一originからのJSON要求だけを受け付けます。

## 招待

共有用で宛先メールを指定し、発行したリンクをコピーして相手へ渡します。メールの自動送信はありません。
自分・既存参加者への招待は拒否します。宛先は前後空白を除去して小文字化します。

トークンは32バイトの乱数を64桁のhexとして発行し、DBにはSHA-256のみを保存します。
リンクは発行から7日間有効です。同じワークスペース・宛先へ再発行すると旧リンクは失効します。
発行直後の応答だけが生のトークンを含み、ワークスペースや受信招待の一覧には含めません。
Cloud開発サーバーの転送ログは招待URLのトークンを伏せ、ブラウザQAは招待画面のスクリーンショットを保存しません。

リンクを開いた利用者は、招待されたメールと一致する登録済み・有効なアカウントでログインします。
未認証ならログイン後に招待ページへ戻ります。本人宛の有効な招待一覧からも参加できます。
招待は利用者の自動登録や、無効なアカウントの再有効化を行いません。
参加は所属の追加と招待の使用済み更新を同じDB処理で確定します。同じ本人の再試行で所属を重複させません。

## DBと検証

`002_workspaces.sql` を追加し、適用済みの `001_auth.sql` は変更しません。
既存DBからの更新・新規初期化は同じmigration管理を使い、環境識別と原文ハッシュを確認します。
アプリのbuildや通常の起動が正式DBへmigrationやseedを実行することはありません。

単一SQL問い合わせのNeon HTTPとCloud PGliteで同じ原子性を保つため、更新はSQL関数内で実行します。
行ロックと一意制約により初期作成・招待再発行・参加・削除の競合を扱います。

ローカルの `qa:cloud` は架空A/BでPC・スマホの操作と個人用分離を検証します。
3人以上の参加と同時承認は単体テスト用PGliteに架空C/Dを追加して確認し、Cloudのログイン対象や正式利用者は増やしません。
正式Previewのmigrationには [専用DB手順](../scripts/db/README.md) に従って対象project・DB・host・環境識別を照合します。
