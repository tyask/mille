## 目的・背景

P1「献立の手動記録と閲覧」の最初の実装単位として、家族のワークスペースで献立・料理・食材を安全に保存し、取り出せる基盤を作る。

## 対象範囲・対象外

- 最新の `main` を基点に、`003_meals.sql` と初期化SQLの生成物を追加・更新する。既存の移行ランナー、環境識別、適用済みSQLのハッシュ照合を使う。
- Meal DTO・Zodスキーマと、献立の取得・作成・更新・削除を扱うサーバー側Repositoryを追加する。変更は単一のDBコマンドで処理し、現在の利用可否、ワークスペース所属、対象と子データの所属、期待版をDB内で照合する。
- HTTP API・コピー・料理名検索・HTTP再送契約はP1b、献立画面はP1cで扱う。

## 受入条件

- [ ] AC-01: 空DBの初期化と002適用済みDBからの増分移行が成功する。既存001・002の原文と既存データを保持し、同じ移行を再実行しても重複適用されない。
- [ ] AC-02: 実在する日付・朝昼夕・料理名で記録できる。任意の人数・食材・分量原文・レシピを扱い、設計の入力上限、レシピ本文とURLの排他、不正値の拒否を確認する。
- [ ] AC-03: 有効な共有ワークスペースの所属者は献立を取得・変更できる。所属外、無効な利用者、別の献立に属する料理・食材IDの指定を拒否する。
- [ ] AC-04: 同一ワークスペース・日付・食事区分の重複、古い版による更新・削除を拒否する。同時操作と保存途中の失敗を再現し、変更の競合や失敗で既存の親子データが部分的に変わらないことを確認する。
- [ ] AC-05: PGliteで移行とRepositoryの回帰を検証する。最終SHAで別Agentのレビュー、lint・型検査・テスト・build・ローカルブラウザQA、GitHub CI、正式PR Previewの同一SHAとPC・スマホ × 架空A/Bを確認する。主要な競合は専用Preview DBの独立した接続でも検証する。
